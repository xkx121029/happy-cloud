## 第二部分：问题详情与修复建议

### S1 配额重复扣减（严重）

- **位置**：[purgeTree](file:///d:/xkx/xkx_appproj/happy_teach/happy_cloud/backend/internal/handler/files.go#L816-L848)、[ClearTrash](file:///d:/xkx/xkx_appproj/happy_teach/happy_cloud/backend/internal/handler/files.go#L475-L487)、[DeletePermanent](file:///d:/xkx/xkx_appproj/happy_teach/happy_cloud/backend/internal/handler/files.go#L451-L472)
- **描述**：`ClearTrash` 一次性 `Find` 全部回收站记录（文件夹及其所有子文件都在列表内），逐个调用 `purgeTree`。`purgeTree(文件夹)` 会递归删除子文件并扣减配额；随后循环再次对子文件调用 `purgeTree`，配额被**第二次扣减**（`GREATEST(quota_used - size, 0)` 只能防止负数，不能防止重复扣）。`DeletePermanent` 批量传入"文件夹+子文件"同样触发。结果：`quota_used` 小于真实占用，用户可超配额上传。
- **触发条件**：回收站同时存在文件夹 A 与 A 内子文件 B，执行"清空回收站"或批量勾选 A、B 后"彻底删除"。
- **修复建议**：
  1. 配额扣减前判断记录是否仍存在（`RowsAffected` 或先查后删）；
  2. 批量接口去重：过滤掉"已是其他待删文件夹后代"的条目；
  3. 推荐将配额扣减与删除封装在事务中，并只对递归树的"根节点"扣减。

### S2 幽灵文件（严重）

- **位置**：[restoreTree](file:///d:/xkx/xkx_appproj/happy_teach/happy_cloud/backend/internal/handler/files.go#L798-L813)
- **描述**：`Restore` 对任意回收站节点单独恢复，不检查父目录状态。场景：文件夹 A（含子文件 B）整体入回收站 → 在回收站仅恢复 B → B `is_deleted=0` 但父 A 仍 `is_deleted=1`。B 既不出现在正常列表（需进入 A，而 A 在回收站不可进入），也不出现在回收站列表（按 `is_deleted=1` 查询）→ 文件永久不可见、无法操作、持续占配额。
- **触发条件**：Trash.vue 中先勾选文件夹 A，再勾选子文件 B，仅恢复 B（前端列表按 `updated_at` 倒序，不保证文件夹先恢复；用户也可手动单选子文件恢复）。
- **修复建议**：`restoreTree` 递归恢复时先向上检查祖先链，若祖先仍在回收站则一并恢复（或返回错误提示"请先恢复父文件夹"）。

### S3 回收站共享文件越权下载（高危）

- **位置**：[DownloadShared](file:///d:/xkx/xkx_appproj/happy_teach/happy_cloud/backend/internal/handler/shared.go#L79-L92)、[moveToTrash](file:///d:/xkx/xkx_appproj/happy_teach/happy_cloud/backend/internal/handler/files.go#L778-L795)
- **描述**：`moveToTrash` 软删除时未重置 `is_shared`；`DownloadShared` 查询 `id = ? AND is_shared = 1 AND type = 1` 无 `is_deleted = 0` 过滤。用户将共享文件移入回收站后，知道 `file_id` 的任何登录用户仍可下载该文件（`ListShared` 有过滤所以列表消失，但直连下载接口绕过）。
- **触发条件**：用户 A 共享文件到公共目录 → 删除（移入回收站）→ 用户 B 调用 `/files/shared/download?file_id=X`。
- **修复建议**：`DownloadShared` 增加 `is_deleted = 0`；`moveToTrash` 时同步重置 `IsShared = 0`。

### S4 分享链接对回收站文件仍有效（高危）

- **位置**：[GetShare](file:///d:/xkx/xkx_appproj/happy_teach/happy_cloud/backend/internal/handler/share.go#L61-L93)、[DownloadShare](file:///d:/xkx/xkx_appproj/happy_teach/happy_cloud/backend/internal/handler/share.go#L122-L174)、[CreateShare](file:///d:/xkx/xkx_appproj/happy_teach/happy_cloud/backend/internal/handler/share.go#L26-L58)
- **描述**：三处查询均不校验 `is_deleted`。文件移入回收站后分享链接仍可访问、下载；`CreateShare` 甚至可对回收站文件新建分享。
- **触发条件**：创建分享 → 移入回收站 → 访问分享链接。
- **修复建议**：查询统一加 `is_deleted = 0`。

### S5 Preview 存储型 XSS（高危）

- **位置**：[Preview](file:///d:/xkx/xkx_appproj/happy_teach/happy_cloud/backend/internal/handler/files.go#L622-L669)
- **描述**：`.html/.htm` 文件以 `text/html; charset=utf-8` + `Content-Disposition: inline` 返回。用户上传含恶意脚本的 HTML 文件后，任何持有预览 URL（需登录态 JWT，存储于 localStorage）的受害者访问 `/api/files/preview?file_id=X` 时，脚本在应用同源下执行，可窃取 localStorage 中的 token、操作账号。
- **触发条件**：上传恶意 `.html` → 诱导他人（或自己误点）访问预览 URL。
- **修复建议**：将 `.html/.htm/.svg` 从内联预览白名单移除（强制 `attachment` 或降级为 `text/plain`）；或对预览响应增加 `Content-Security-Policy: sandbox; default-src 'none'`。

### S6 分片上传跨用户污染（高危）

- **位置**：[UploadChunk](file:///d:/xkx/xkx_appproj/happy_teach/happy_cloud/backend/internal/handler/files.go#L180-L202)、[UploadMerge](file:///d:/xkx/xkx_appproj/happy_teach/happy_cloud/backend/internal/handler/files.go#L205-L289)、[ChunkDir](file:///d:/xkx/xkx_appproj/happy_teach/happy_cloud/backend/internal/util/util.go#L59-L61)
- **描述**：`ChunkDir(hash)` 为全局共享目录 `storage/tmp/<hash>`（不含 user_id）。用户 A、B 上传相同 hash 的分片时互相覆盖/混入，A 合并时可能把 B 的分片合并进自己的文件，造成文件损坏与跨用户数据污染。且 `UploadMerge` 不校验分片归属，合并后只校验大小不校验内容 hash。
- **触发条件**：两名用户同时（或先后）上传内容哈希相同的文件。
- **修复建议**：`ChunkDir` 中加入 userID；`UploadMerge` 合并后重新计算并比对 `req.Hash`；分片写入前限制单片大小。

### M1 分享过期时间无法清除（中危）

- **位置**：[UpdateShare](file:///d:/xkx/xkx_appproj/happy_teach/happy_cloud/backend/internal/handler/share.go#L270-L310)、[Shares.vue](file:///d:/xkx/xkx_appproj/happy_teach/happy_cloud/web/src/views/user/Shares.vue#L89-L105)
- **描述**：后端注释与前端 API 注释均声明"expire_at 传 null 表示永久"，但 `if req.ExpireAt != nil { s.ExpireAt = req.ExpireAt }` 使 null 不更新。用户在"设置"中选择"永久"（前端发送 `expire_at: null`）后，原过期时间保持不变，链接仍会过期。
- **触发条件**：对设置了有效期的分享，编辑改为"永久"并保存。
- **修复建议**：区分"未传"与"null"——增加 `ClearExpire *bool` 字段，或对 `req.ExpireAt == nil` 时置 `s.ExpireAt = nil`（并让前端省略字段表示不修改）。

### M2 预览 Content-Type 映射错误（中危）

- **位置**：[Preview](file:///d:/xkx/xkx_appproj/happy_teach/happy_cloud/backend/internal/handler/files.go#L640-L665)
- **描述**：`.webm/.ogg/.mov/.m4v` 均返回 `video/mp4`；`.wav/.flac/.m4a/.aac` 均返回 `audio/mpeg`。浏览器按错误 MIME 解码，webm/ogg/mov 视频与 wav/flac 音频无法正常播放（前端 PreviewDialog 用 blob 播放，blob 类型错误导致 `<video>`/`<audio>` 解码失败）。
- **触发条件**：预览任意 webm/ogg/mov/wav/flac 文件。
- **修复建议**：按扩展名精确映射（webm→video/webm、ogg→video/ogg（音频为 audio/ogg 时需按内容）、mov→video/quicktime、m4v→video/mp4、wav→audio/wav、flac→audio/flac、m4a→audio/mp4、aac→audio/aac）。

### M3 恢复重名冲突（中危）

- **位置**：[restoreTree](file:///d:/xkx/xkx_appproj/happy_teach/happy_cloud/backend/internal/handler/files.go#L798-L813)
- **描述**：恢复时不调用 `checkNameDup`。用户删除文件 B 后，在同目录新建同名文件，再恢复旧 B → 同目录出现两个同名文件，破坏"同目录名称唯一"假设，后续重命名、移动、UI 均受影响。
- **触发条件**：删除 → 重建同名 → 恢复。
- **修复建议**：恢复时对每个节点执行 `checkNameDup`，重名时用 `uniqueName` 自动加后缀或返回 409。

### M4 转送不校验回收站状态（中危）

- **位置**：[SendTransfer](file:///d:/xkx/xkx_appproj/happy_teach/happy_cloud/backend/internal/handler/transfer.go#L42-L101)、[AcceptTransfer](file:///d:/xkx/xkx_appproj/happy_teach/happy_cloud/backend/internal/handler/transfer.go#L116-L164)
- **描述**：`SendTransfer` 查询无 `is_deleted=0`，可发送回收站文件；`AcceptTransfer` 同样不校验 `src` 的 `is_deleted`，可接收已删除文件（实体仍在磁盘）。
- **修复建议**：两处查询统一加 `is_deleted = 0`。

### M5 分享链接指向 API 而非页面（中危）

- **位置**：[ShareDialog.vue](file:///d:/xkx/xkx_appproj/happy_teach/happy_cloud/web/src/components/ShareDialog.vue#L24-L29)、[share.go CreateShare](file:///d:/xkx/xkx_appproj/happy_teach/happy_cloud/backend/internal/handler/share.go#L57)
- **描述**：后端返回 `url = "/api/share/TOKEN"`（API 接口地址，返回 JSON）。ShareDialog 拼接为 `origin/api/share/TOKEN`，用户复制/预览打开的是 JSON 数据而非分享落地页；而 Shares.vue 用的是 `/share/TOKEN`（前端路由），两处链接格式不一致。
- **触发条件**：创建分享后点击"复制"/"预览分享"。
- **修复建议**：ShareDialog 直接用 `${window.location.origin}/share/${token}` 生成链接（忽略后端 url 字段），或后端返回不带 `/api` 前缀的路径。

### M6 存储概览初始不加载（中危）

### M7 PreviewDialog blob URL 泄漏（中危）

### M8 存储口径矛盾（中危）

- **位置**：[moveToTrash](file:///d:/xkx/xkx_appproj/happy_teach/happy_cloud/backend/internal/handler/files.go#L778-L795)、[StorageOverview](file:///d:/xkx/xkx_appproj/happy_teach/happy_cloud/backend/internal/handler/files.go#L672-L702)
- **描述**：`moveToTrash` 不扣减配额（注释却写"不再计为正常占用"），配额在 `purgeTree` 才扣减 → 回收站文件仍占配额。但 `StorageOverview` 只统计 `is_deleted=0`，分类之和小于 `quota_used`，StorageCard 中"已用空间"与分类占比矛盾。回收站文件"是否占用配额"为设计决策，但统计口径不一致是事实问题。
- **修复建议**：二选一：回收站占用配额 → StorageOverview 统计回收站文件并在 UI 标注；回收站不占配额 → `moveToTrash` 时扣减、`restoreTree` 时加回（需处理 S1 重复扣问题）。

### M9 Views 计数竞态与提前计数（中危）

- **位置**：[GetShare](file:///d:/xkx/xkx_appproj/happy_teach/happy_cloud/backend/internal/handler/share.go#L72-L73)
- **描述**：`share.Views++; UpdateColumn` 为读-改-写非原子操作，并发访问丢失更新；且密码未验证时也计数，密码错误重试会重复 +views。
- **修复建议**：`UpdateColumn("views", gorm.Expr("views + 1"))` 原子自增；仅在密码校验通过后计数。

### M10 管理端更新用户返回旧数据（中危）

### M11 记住我明文密码（中危）

- **位置**：[Login.vue](file:///d:/xkx/xkx_appproj/happy_teach/happy_cloud/web/src/views/user/Login.vue#L39-L42)、[settings.ts persist](file:///d:/xkx/xkx_appproj/happy_teach/happy_cloud/web/src/stores/settings.ts#L72-L83)
- **描述**：明文密码写入 localStorage（`happy_cloud_settings`），并经 `SaveSettings` 持久化到后端数据库。任何 XSS/本地访问者均可窃取。
- **修复建议**：改为"记住用户名"；如需记住登录态应使用更长有效期的 JWT/Refresh Token 而非明文密码。

### M12 合并后不校验内容 hash（中危）

- **位置**：[UploadMerge](file:///d:/xkx/xkx_appproj/happy_teach/happy_cloud/backend/internal/handler/files.go#L271-L274)
- **描述**：仅校验 `fi.Size() != req.Size`，不校验合并文件内容与 `req.Hash` 是否一致。恶意客户端可上传任意内容并声明任意 hash，后续 `UploadHash` 秒传命中该 hash 时将获得错误内容。
- **修复建议**：合并后重新计算 SHA256 并比对 `req.Hash`。

### M13 递归删除/恢复无事务（中危）

- **位置**：[moveToTrash](file:///d:/xkx/xkx_appproj/happy_teach/happy_cloud/backend/internal/handler/files.go#L778-L795)、[restoreTree](file:///d:/xkx/xkx_appproj/happy_teach/happy_cloud/backend/internal/handler/files.go#L798-L813)、[purgeTree](file:///d:/xkx/xkx_appproj/happy_teach/happy_cloud/backend/internal/handler/files.go#L816-L848)
- **描述**：每个节点独立 DB 操作、无事务包裹，中途失败（DB 错误/进程中断）留下部分已删/已恢复的数据；超大目录递归深度即目录深度，存在栈溢出风险。
- **修复建议**：用 `db.DB.Transaction` 包裹整棵树的更新；深度受限或改为迭代遍历。

### 低危项说明（L1-L16）

- **L1** 配额检查与 `updateQuota` 非原子（files.go:136-139/223-226/717-720、transfer.go:142-144）：并发上传可超配额。建议 `UPDATE ... SET quota_used = quota_used + ? WHERE quota_used + ? <= quota_max` 条件更新。
- **L2** Mkdir/Rename/Upload 未过滤文件名特殊字符（`/`、`\`、控制字符、超长）。存储路径基于 hash 无穿越风险，但下载响应头与 UI 异常。建议按白名单/黑名单校验并限制长度。
- **L3** Favorite 表缺 `(user_id, file_id)` 唯一索引（model.go:36-41），并发收藏重复。建议加唯一索引 + `FirstOrCreate`。
- **L4** `Content-Disposition: filename*=UTF-8''` 后接 `url.QueryEscape`（files.go:308、share.go:172、shared.go:90），空格变 `+`。应使用 RFC 5987 百分号编码（`%20`）。
- **L5** AdminDeleteFile 将 `f.Name` 当用户名传入 purgeTree 日志（admin.go:134）。
- **L6** Stats `storage_used` 未过滤 `is_deleted`（admin.go:148），含回收站文件，与 StorageOverview 口径不一致。
- **L7** `/api/routes` 未鉴权（main.go:101-110），暴露接口清单。建议至少要求登录。
- **L8** ClearTrash/DeletePermanent 对已删除记录再次执行时 `purged` 计数虚高（GORM 对不存在记录 `Delete` 返回 nil error，RowsAffected=0）。
- **L9** Trash.vue:138 "删除后 30 天内可恢复"：后端无任何 30 天自动清理逻辑，文案不实。
- **L10** MoveDialog 批量移动时未排除"自身"为目标（file 为 null 时 `loadFolders` 不过滤，MoveDialog.vue:29），选中文件夹 A 后目标列表含 A，后端静默跳过。
- **L11** download.ts:29 `a.click()` 后立即 `revokeObjectURL`，Firefox 下可能中断下载（需进一步确认浏览器行为）。
- **L12** CORS 未匹配时回显任意 Origin 且带 `Access-Control-Allow-Credentials: true`（auth.go:97-99）。当前鉴权用 Bearer header 非 Cookie，实际风险有限（需进一步确认）。
- **L13** GetShare 响应结构 `{share, file, files, password_required}` 与前端 `ShareInfo` 类型（token/url 字段）不符（types.ts:87-93），当前未使用受影响字段。
- **L14** SharePreview 密码验证成功后 `load()` 二次调用 GetShare 再次 +views（与 M9 同根因）。
- **L15** RecentFiles 按 `updated_at` 排序，模型无对应复合索引，数据量大时查询慢（需进一步确认数据规模）。
- **L16** 分片残留：失败上传在 `tmp/<hash>` 留下旧分片，后续同 hash 上传时 `len(parts)` 判断可能误判（与 S6 同根因）。建议 merge 成功后清目录、失败时按时间清理。
